# 长文本链路修复（v1.2.0，2026-09-18）

## 症状

在「合成并试听」里填一段较长的文字（例如把「你好，欢迎使用阅读，这是手机 MNN 本地合成测试。」重复 3 遍，
共 92 字），听到的却只有**开头一句**，剩下的没了；短文本也会偶发同样问题。

## 三个真因（互相独立，都已修）

### 1. 采样器没有任何重复惩罚（最关键）

`cosyvoice_ras` 是这套定制 MNN 引擎里的采样器，它的管线是**写死**的
`range → topK → topP → select`，**不含 `penalty` 步**；而 `repetition_penalty` 只在 `penalty` 步里生效，
MNN 默认的 `mixed_samplers` 也不含它。也就是说这套 LLM 从来没有过重复惩罚 —— 一旦开始重复就再也出不来。

实测同一句 92 字（hexagon 后端）：

| 采样器 | 尝试次数 | 生成 token | EOS | unique | 最长连续重复 | 结果 |
|---|---:|---:|---|---:|---|---|
| `cosyvoice_ras`（旧） | 6 | 500 / 952 | ✗ 全部 | 57~219 | 33 / 314 / 345 / 610 / 858 | 全部被质量门拒绝 |
| `mixed` + `penalty` + `repetition_penalty=1.15` | **1** | **590** | **✓** | — | — | **首次尝试即接受，成品 23.56 s** |

### 2. `maxTokens` 写死 500 ≈ 只够 20 秒语音

这条链的 LM 生成的是「音色前缀文本 + 正文」**整段**（前缀里那 25 个字的参考文本同样占 token）。
实测约 6 token/字：39 字 → 184 token；63 字 → 353~443；92 字 → 必然撞满 500。
改为按字长估算 `(前缀字数 + 正文字数) * 8 + 128`，钳在 `[500, 1024]`。

### 3. 质量门判据把「正常输出」也拒了

旧判据 `longestRun >= 8 即拒` 在长输出上误杀：同一句 63 字的 7 次尝试里，有 4 次是**正常终止**
（370~387 token、有 EOS、unique 230~246），最长连续段只有 8~20 个 token（约 0.3~0.8 秒），
在语音 token 里对应长元音/静音/拖音。新判据只保留三条能证明退化的条件：

```text
1. 没有 EOS                生成只可能在 EOS 或 maxTokens 处停下，没 EOS 就是撞满上限
2. unique <= 4 且长度 >= 20  灾难性坍缩
3. 单段连续重复 >= 64        本次"正常"最大 20、"跑飞"最小 105，64 落在两者之间
```

并新增**尾部空转裁剪**：没有 EOS、重复段一直延伸到序列末尾、重复段 ≥32 且保留段 ≥32 时，
切掉重复段并重写 `speech-tokens-0.csv`（同时写 `llm-tail-repair.txt` 留证，不静默处理）。

## 另外两处

- **按明文长度分流已取消**：原来「≤24 字走 NPU、否则走 OpenCL」，依据是「NPU 长序列约 3/4 退化」。
  但那个结论的判据字段（`continuousHexagon` / `npuFirstTokenValid`）经查**只是配置回显**，
  不是运行期测量；判据本身又是上面那个误杀的阈值。拆掉两条腿后实测同一句 63 字：
  **hexagon 4/4 首次尝试即通过**，prefill 0.62~0.73 s（OpenCL 要 10.8~22.9 s），
  现在一律用硬件策略给出的后端。
- **每一次尝试都过质量门**：原来只有第一次过门，最后那次 CPU 兜底跑完直接交付 —— 而 CPU 恰是
  退化率最高的那条路，等于把退化音频悄悄送出去。现在尝试计划是
  「路由后端 5 次 → CPU 兜底 2 次」，全不过就报错，不再交付。

## 实测（v1.2.0）

| 场景 | 结果 |
|---|---|
| 试听 · 短文本 | LLM wall **3.05 s** / **67.2 tok/s**（150→155 token），首次即接受 |
| 试听 · 短文本 | **3.32 s** / **58.7 tok/s**，首次即接受 |
| 试听 · 长文本 | **11.94 s** / **47.6 tok/s**（231→452 token），首次即接受 |
| 音色创建（文字设计音色） | 闭环 **97.3 s**（prefill 19.4 s / decode 61.5 s / decoder 6.6 s / enroll 6.4 s） |

对照修复前同一句 92 字：5 次 NPU（每次 13~33 s）+ 2 次 CPU（87 s）**全部被质量门拒**，
几分钟，最后交付的还是截断音频。

## 附带：注册用参考文本从 26 字缩到 15 字

注册时音频会被 `MAX_REALTIME_PROMPT_TOKENS = 125`（= 5.0 秒 / 250 帧）截断，多出来的直接丢；
而 `promptPrefix` 里存的仍是**完整文本**，于是文本提示与音频提示不对齐
（旧默认 26 字设计出 7.68 秒 → 截到 5.0 秒，前 5 秒只覆盖前约 17 个字）。
改为 15 字（对齐内置基准音色 `builtin-mnn-reference-v1` 的 15 字 / 87 token / 3.48 秒）。
实测新默认：设计出 **4.08 秒 / 102 token，没有被截断**。
`design.json` 现在记录 `promptTokenCount` / `promptFrameCount` / `promptTruncatedByRealtimeLimit`。
